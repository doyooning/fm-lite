# /verify — 구현 검증

인자: 명세서 경로(선택). 생략 시 `docs/specs/`의 최신 명세서를 대상으로 삼되 사용자에게 확인한다.

## 1. 변경 파악

```bash
git status --short
git diff --stat
```
- 명세서의 "변경 파일 목록"과 실제 diff를 대조한다. **명세에 없는 파일이 변경됐으면 그 자체가 지적 사항**이다.
- diff 본문을 읽는다 (`git diff`). 테스트가 통과해도 스펙과 다르게 구현된 부분은 여기서만 잡힌다.

## 2. 자동 검증 실행

순서대로 실행하고 각 결과를 기록한다. 실패해도 멈추지 말고 나머지도 돌려 전체 상황을 파악한다.

```bash
# 백엔드 — 컴파일 + 단위/밸런스 테스트
cd backend && ./gradlew test        # PowerShell이면 .\gradlew.bat test

# 프론트 — 타입 + 린트 + 빌드
cd frontend && npx tsc --noEmit
cd frontend && npm run lint
cd frontend && npm run build
```

DB/API 흐름까지 바뀐 변경이면 E2E도 돌린다 (백엔드·DB가 떠 있어야 함 → `/dev` 참조):

```bash
node tools/e2e-test.mjs            # 인증 포함 풀 플로우
node tools/auth-e2e.mjs            # 인증만
```

시뮬레이션 판정(`match/simulation/`)이 바뀌었다면 `MatchEngineBalanceTest`의 몬테카를로 결과를
반드시 확인한다 — 평균 득점 2.5~3.0, 강팀 대 약팀 승률 70~80% 범위 이탈은 실패로 본다.

## 3. 수용 기준 대조

명세서의 체크박스를 하나씩 **근거와 함께** 판정한다. 근거는 파일:라인 또는 테스트 출력.

| 기준 | 판정 | 근거 |
|---|---|---|
| ... | ✅ / ❌ / ⚠️ | `MatchService.java:142` / 테스트 로그 |

판정 불가 항목(예: 화면 확인 필요)은 ⚠️로 두고 사용자에게 수동 확인을 요청한다 — 임의로 ✅ 처리하지 않는다.

## 4. 추가 점검 (diff를 읽으며)

- 새 엔드포인트에 인증/소유권 검증이 빠지지 않았는가
- `ApiResponse` 래퍼와 에러 코드 규약을 지켰는가
- 마이그레이션이 기존 `V*.sql` 수정이 아닌 **새 파일**인가, `db/supabase-init.sql` 동기화가 필요한가
- 프론트 타입이 백엔드 DTO와 실제로 일치하는가 (불일치 의심 시 `/api-sync`)
- 커밋되면 안 되는 파일(`env/`, `*.yml`, `.env*`)이 스테이징에 섞이지 않았는가

## 5. 리포트

사용자에게 이 형식으로 보고한다:

```
검증 결과: 통과 N / 실패 M / 확인필요 K

실패
1. [항목] — 무엇이 왜 틀렸는지 + 파일:라인
...

권장 조치: /handoff 로 재작업 지시서 생성 (실패 항목 포함)
```

실패가 있으면 임의로 고치지 말고 재작업 지시서를 만든다(구현은 Codex 담당).
단, **오타 수준의 1~2줄 수정**은 직접 고치고 무엇을 고쳤는지 보고한다.
